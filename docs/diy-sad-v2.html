System Overview & Goals

1.1 Competition Context

The CAT Robotics Culture Club DIY Robot Challenge 2026 is an autonomous outdoor obstacle-course race. Teams build custom robots competing on a speed course (3 laps) and an obstacle course (2 laps). Scoring is time-based with cumulative penalties for skipped obstacles.

CommunicationNone during run (Rule 2.4)E-Stop exempt

1.2 Design Goals

MVP — Reliable 2-Lap Completion

Complete both laps of the obstacle course within 10 minutes using correct behaviors (push-through vs navigate-around) for each obstacle type. Zero GPS dependency — localization entirely from LiDAR + IMU + encoders against pre-built map.

Stretch — Sub-4-Minute Run

Zero obstacle skips, consistent 2-lap completion under 4 minutes with sub-5cm localization accuracy at critical waypoints. cuVSLAM provides visual-inertial redundancy in case of LiDAR degradation.

Why Dead-Wheel Encoders Instead of Motor Encoders?
FWD motor encoders measure wheel rotation — but on gravel, inclines, and turns the driven wheels slip, producing false odometry that corrupts the EKF. Dead-wheel encoders are mounted on passive, non-driven wheels that maintain ground contact without slip. They provide reliable twist (dx, dy, dθ) at 50-100 Hz that fills the gap between 10-20 Hz LiDAR scans.

Compute Architecture

3.1 Responsibilities Split

STM32 — Real-Time Layer
  • CAN bus: /cmd_vel → motor frames
  • E-Stop: wired + wireless → cmd=0 within 1s
  • Watchdog: wireless signal lost >800ms → auto-stop
  • micro-ROS bridge over UART to Jetson
Jetson Orin Nano — ROS 2 Stack
  • All sensor drivers (LiDAR, IMU, camera, encoders)
  • FAST-LIO2 LiDAR-inertial odometry (CPU)
  • robot_localization EKF (CPU)
  • Nav2 planner + controller (CPU)
  • cuVSLAM visual odometry (GPU — stretch)
  • Mission state machine + behavior switcher

4.2 Localization — Multi-Level EKF (No GPS)

With RTK GPS rejected, localization relies entirely on FAST-LIO2 + dead-wheel encoders + ACEINNA IMU fused in a local EKF, with AMCL/NDT providing the global map→odom correction.

Figure 2 — EKF Fusion Architecture

FAST-LIO2 — Primary Odometry

PropertyValue
AlgorithmIterative Extended Kalman Filter (iEKF) on point-to-plane
Inputs/hesai/points + /imu/data
Output/lidar_odom (Odometry) @ 10-20 Hz
Drift (calibrated)0.1–0.3% of distance traveled
Tunnel behaviorRich wall features — no degradation

EKF Local — robot_localization

Inputs:
  /lidar_odom    (FAST-LIO2, pose+twist, 10-20Hz)  — weight: HIGH
  /wheel/odom    (encoders, twist only, 50-100Hz)   — weight: MEDIUM
  /imu/data      (ACEINNA, angular vel, 200Hz)      — weight: MEDIUM (prediction)
  /visual_odom   (cuVSLAM, pose+twist, 30Hz)       — weight: MEDIUM [STRETCH]

Output:  /odom/filtered  (high-rate fused odometry)
Frame:   odom → base_link
Purpose: Feeds Nav2 MPPI controller — low latency, high rate

Global Localization — AMCL / NDT Match

Method:  Match live LiDAR scans against pre-built map
Output:  map → odom transform (corrects accumulated drift)
Rate:    ~1-5 Hz (matching frequency)
Purpose: Provides global consistency without GPS
Note:    No navsat_transform needed — purely map-based

4.3 Perception — PCL Obstacle Classifier

Pipeline (per LiDAR scan, ~20Hz):
  1. Ground removal     → RANSAC plane fit, remove points within 5cm
  2. Clustering         → Euclidean extraction (tolerance: 0.15m)
  3. Map differencing   → Compare vs prior_map.pcd (new obstacles only)
  4. Classification     → Per-cluster: CHIMES / MOVABLE / TUNNEL / WALL
  Output: /obstacle_class (zone_id, classification, confidence)

4.4 Navigation — Nav2

Global: Smac Hybrid-A*

Non-holonomic path planning respecting turn radius. Pre-computed from centerline waypoints. Re-invoked only on WALL classification.

Local: MPPI Controller

Samples thousands of trajectory rollouts. Smooth velocity profiles on gravel/ramps. Better than DWB for dynamic obstacles.

Multi-Level EKF Fusion Design

This is the core localization architecture. With no GPS, all global consistency comes from map matching. The EKF fuses multiple odometry sources for high-rate, low-latency local pose estimates.

5.1 Source Characteristics

SourceProvidesRateStrengthWeakness
FAST-LIO2Full 6DOF pose + twist10-20 HzBest absolute accuracy (0.1-0.3% drift)Degrades in featureless areas, lower rate
Dead-wheel encoders2D twist (dx, dy, dθ)50-100 HzHigh rate, fills LiDAR gaps, no slip2D only, no vertical, accumulates drift
ACEINNA IMUAngular vel + linear accel200 HzHighest rate, prediction between updatesDouble-integration drift (mitigated by 1.3°/hr bias)
cuVSLAM (stretch)Full 6DOF pose + twist30 HzGPU-only (0% CPU), independent modalityFails in darkness/texture-poor areas

5.3 TF Tree

Figure 4 — TF Frame Tree
Critical — No navsat_transform
With GPS removed, there is NO EKF2/navsat_transform. The map→odom transform comes from AMCL or NDT matching the live scan against the pre-built map. This is simpler but requires a high-quality prior map. Map building is the #1 priority in June.

5.4 Accuracy Expectations (No GPS)

ScenarioExpected AccuracyNotes
FAST-LIO2 alone, calibrated5–15cm per full lapOutdoor, mixed terrain
+ Encoders + IMU in EKF3–8cm per lapEncoder twist fills scan gaps
+ AMCL map matching (open area)<5cm absoluteContinuous drift correction
+ cuVSLAM redundancy (stretch)<3cm absoluteIndependent visual confirmation
Inside tunnel (no GPS anyway)~5–10cm drift over lengthRich wall features for LiDAR
Narrow Passage Requirement
Track width 20" − robot 16" = 4" total clearance (2" per side = 5cm). Need lateral accuracy <4cm at passage entry. AMCL correction immediately before narrow passages provides this. Failsafe: slow to 0.1 m/s and hold heading through passage.

GPU Acceleration & cuVSLAM

The Jetson Orin Nano's 40 TOPS GPU is largely idle in the base configuration. This section documents what can (and cannot) be offloaded to GPU.

6.1 CUDA Offloading Reality Check

ComponentCUDA Accelerated?Reality
Hesai LiDAR driverNoJust UDP packet parsing — trivial CPU load (~4%)
RealSense driverNoDepth computed on-sensor ASIC, not host CPU
Isaac ROS image_procYesGPU rectification/resize of camera images
Isaac ROS depth_image_procYesGPU depth→pointcloud conversion
cuVSLAMYesFull visual SLAM on GPU — zero CPU cost
NvbloxYes3D costmap on GPU (replaces CPU costmap2D)
FAST-LIO2NoCPU-only iEKF — no CUDA path exists
Nav2 planner/controllerNoCPU-only — no CUDA path exists
PCL/NDTPartialndt_omp uses OpenMP (CPU threads), not CUDA
Bottom Line
The raw sensor drivers are NOT CPU-heavy — there's nothing meaningful to offload. The real GPU value comes from cuVSLAM (visual odometry) and potentially Nvblox (3D costmap). FAST-LIO2 and Nav2 remain CPU-bound regardless.

6.3 Nvblox — 3D Costmap (August Stretch)

If cuVSLAM works well in July, consider Nvblox in Aug 1-15. Nvblox builds a GPU-accelerated 3D TSDF/ESDF costmap from depth images. Benefits: better obstacle representation than 2D voxel layer, handles overhanging obstacles. Risk: adds complexity near feature lock. Only pursue if specific obstacle types require 3D reasoning.

Key Decisions & Rejected Alternatives

❌ Rejected: RTK GPS (BX992 — $2,500)

Rationale: $2,500 receiver + $1,000+/yr correction service + base station setup + antenna integration. LiDAR-based localization (FAST-LIO2 + AMCL) achieves <5cm accuracy without any of this infrastructure. GPS degrades near buildings/trees (common on outdoor courses). The tunnel obstacle makes GPS useless for a significant portion of the track anyway.

What replaces it: AMCL/NDT matching against pre-built map provides map→odom transform. Dead-wheel encoders provide high-rate twist. Combined with FAST-LIO2's excellent accuracy, no GPS needed.

✅ Accepted: Dead-Wheel Encoders

Rationale: Non-driven wheels don't slip — unlike motor encoders on FWD. Provides reliable 50-100 Hz twist that fills the 50-100ms gaps between FAST-LIO2 LiDAR updates. Critical for smooth MPPI controller inputs. Low cost (~$50-100 for two rotary encoders + mounting).

✅ Accepted: ACEINNA MTLT335D Industrial IMU

Rationale: 1.3°/hr gyro bias stability (vs >10°/hr for consumer IMUs). CAN/RS232 interface (no USB latency jitter). Temperature-compensated. The single largest factor in FAST-LIO2 accuracy is IMU quality — this is worth the cost.

✅ Accepted: cuVSLAM as Stretch Goal (July)

Rationale: Runs entirely on Orin Nano GPU (0% CPU impact). Provides independent visual-inertial odometry from D435i stereo. If FAST-LIO2 degrades (featureless area, dust), cuVSLAM maintains localization. 2-3 hour integration once base stack works.
